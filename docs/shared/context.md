# Priamus Trips — Shared Context

Top-level context for the Priamus Trips project. This file is shared by backend, frontend, and devops work, and contains decisions that span the entire system.

For backend-specific rules see `docs/backend/context.md`. For frontend-specific rules see `docs/frontend/context.md`.

---

## 1. Product overview

Priamus Trips is the digital management and monitoring system for freight trips operated by Priamus Ecologica S.r.l.

Two user-facing surfaces:
- **Driver PWA** (smartphone, BYOD): drivers record their trips during or at the end of the day, with attachments and end-of-day summaries. Optimized for 10-inch tablets in landscape orientation, glove-friendly interaction, minimum touch targets 44×44px (PRD RNF-01), WCAG AA contrast.
- **Back-office web app** (desktop): the secretariat manages master data (customers, contracts, rates, vehicles, drivers), reviews trips, resolves anomalies, exports invoicing data.

**Strict data-boundary rule**: drivers must NEVER see pricing, tariffs, rates, or calculated totals. Financial logic lives server-side and surfaces only in the back-office view.

---

## 2. System architecture (high level)

- **Backend**: .NET 10 modular monolith, ASP.NET Core Minimal API, PostgreSQL 16, JWT bearer auth.
- **Frontend**: Angular 21+ PWA with DaisyUI 4 (corporate theme) + Tailwind CSS.
- **Communication**: REST/JSON over HTTPS, OpenAPI 3.1 generated by the backend, TypeScript client generated for the frontend.
- **Deployment**: Containerized (Docker Compose for development, container orchestration for production — TBD).

Two-track development: backend first, frontend after. The frontend should never get ahead of the backend API contract; the OpenAPI specification is the source of truth for the contract.

## 4. Universal rules (apply everywhere)

These apply across backend, frontend, and infrastructure. No exceptions without documented justification.

### Language

- **Code (identifiers, comments, logs, exception/error messages, file and folder names, namespaces, test names, README, ADR, commit messages) → English, always.**
- **End-user content (UI labels, validation messages shown to the user, generated documents, emails) → Italian, in localization files (`.resx` for backend, Angular i18n or equivalent for frontend).**

### Domain glossary

The shared glossary maps Italian domain terms from the PRD to English code identifiers. See `docs/shared/glossary.md`. Both backend and frontend must use the same glossary; mismatches between layers are a major source of bugs.

### Logical modules

The same logical modules exist on both sides:

| Module | Backend responsibility | Frontend surface |
|---|---|---|
| `Identity` | Authentication, sessions, roles | Login, session management |
| `Registry` | Master data + pricing engine | Back-office only |
| `Operations` | Trips, attachments, daily summaries | Driver PWA + back-office views |
| `BackOffice` | Reporting, exports | Back-office only |

### Time and money

- All time logic uses injected clock abstractions, never the system clock directly. Time-related bugs caught at this layer never make it to production.
- Monetary amounts are typed (`Money` with currency) on the backend, displayed only in the back-office. Drivers never see amounts.

### Authorization

- Backend: every endpoint declares an explicit authorization policy.
- Frontend: every route declares an authorization guard. The driver app and the back-office app have disjoint route sets.

### Errors

- Backend produces `ProblemDetails` responses driven by an `ErrorType` classification (see backend appendices).
- Frontend translates server `errorCode` fields into localized Italian messages from a resource file. Never displays raw server descriptions.

## 5. Out of scope (MVP)

Explicitly NOT to implement; require re-discussion if requested:

Offline mode, push notifications, GPS tracking, OCR of documents, billing system integration, end-customer app, advanced analytics, occasional rented vehicles not in registry, vehicle categorization with category-level pricing, trailer-differentiated pricing, recipient digital signature, automatic invoice generation.

---

## 6. Operational principles

- **Trunk-based development**, short-lived feature branches (< 3 days).
- **PR required** for merges to `main`. CI must pass.
- **Backend-first development**: a frontend feature cannot start before the corresponding backend endpoint exists and is documented in OpenAPI.
- **Documentation tracks code**: changes to architectural rules update this document and the relevant appendices BEFORE the code change is merged.
- **CI gates**: build, tests (unit + integration), linters, the Italian-pattern check (no Italian identifiers in code).
